# Roast Panel — Meet Live Concierge (Phase 3)
**Date:** 2026-05-13
**Round:** 3 (follow-up roast)
**Project:** Server-driven Real-time AI Assistant with cinematic 16:9 Stage and native Doc rendering.
**Audience:** Team / Stakeholders

## Persona 1 — The Paranoid Security Researcher

You've added tickets, but you've opened a new front door for injection.

- **"Native" Rendering is an XSS Playground**: You're taking Markdown from an AI, converting it to HTML on the server, and then injecting it into the DOM on the Stage via `innerHTML` (`main_stage.html` line 343). Even with `bleach`, you're one missing tag or one `data:` attribute bypass away from a session hijack. The Stage has no `nonce` on its scripts and a very loose CSP.
- **The CSP is a "Connect to Everything" Policy**: Your CSP in `main.py` (lines 92-102) includes `unsafe-inline`, `unsafe-eval`, and `connect-src *`. This effectively neuters the browser's ability to protect the user if your "native rendering" leaks an XSS payload. 
- **D2 Local File Read (LFR)**: You're still relying on regex to "clean" D2 code (`app/diagrams.py` lines 14-16). D2 has features for importing local files or executing scripts. A clever prompt to Gemini can still trick it into outputting D2 that reads your `.env.production` or `/etc/passwd` when the `d2` binary processes the file.
- **WebSocket Ticket Reuse**: Are those tickets one-time use? If I sniff a ticket, can I use it to open a parallel connection? You're purging them every 5 minutes, but within that window, they seem to be reusable bearer tokens.

**Gaps:**
| Severity | Problem | Fix direction |
|---|---|---|
| Critical | XSS via `innerHTML` on Stage | Use a dedicated Markdown component that doesn't rely on raw HTML injection, or enforce a strict `Content-Security-Policy` with `nonce`. |
| Significant | D2 Injection / LFR | Use the `d2` binary's own sandboxing flags if they exist, or use a WASM-based D2 renderer that has zero access to the host filesystem. |
| Significant | Loose CSP | Remove `unsafe-inline` and `unsafe-eval`. Tighten `connect-src` to known Google and application domains. |

## Persona 2 — The Impatient UX Designer

You've made it "Cinematic," but you've also made it feel like a slow-motion movie.

- **The 16:9 "Cinematic" Constraint**: You're forcing a 16:9 aspect ratio on the Stage (`main_stage.html` line 52). If the user is on a vertical screen or has a narrow Meet window, your "Cinematic" view will be a tiny postage stamp in the middle of the screen. Meet isn't a movie theater; it's a productivity tool.
- **The Scrolling Card Anti-Pattern**: You're rendering "Native Documents" inside a card with a `max-height: 450px` (`main_stage.html` line 164). If Gemini generates a long project plan, I have to scroll a small window inside a window. Just let the document take the full Stage height.
- **A2UI Latency**: Because the UI components are driven by the server, there's a visible "hop" between Gemini finishing a sentence and the UI actually updating. If the WebSocket jitters, the "Assistant" and the "UI" get out of sync.
- **Transcript Overlay Overlap**: Your transcript layer is a "Permanent Overlay" (`main_stage.html` line 118). If it's active while a diagram is shown, it blocks the bottom 30% of the diagram. You're sacrificing visual clarity for "Cinematic" subtitles.

**Gaps:**
| Severity | Problem | Fix direction |
|---|---|---|
| Significant | Aspect Ratio Friction | Remove the hard 16:9 constraint; use `flex: 1` and `object-fit: contain` to maximize available space. |
| Significant | Transcript Overlap | Move the transcript to a dedicated "Letterbox" area below the diagram/doc, rather than overlaying it. |
| Minor | Scrolling Card | Remove `max-height` on the `markdown-body` and let it expand to fit the Stage. |

## Persona 3 — The Skeptical Credibility Critic

"Phase 3" feels more like "Phase 1: Refactored".

- **"Native Document Rendering" is a Misnomer**: You're converting Markdown to HTML and putting it in a CSS box. That's not native document rendering. Native rendering would be an embedded Google Doc editor or at least a high-fidelity PDF-style view. You're just pretty-printing text.
- **The "update_interface" Tool is a Black Box**: You've given Gemini a tool to "update the interface," but Gemini doesn't actually see the interface. It's flying blind. If the user says "Move that box to the left," Gemini will call `update_interface` with a new status text, but it won't actually move any box.
- **"Cinematic" is a Buzzword**: Aside from the 16:9 ratio and some dark backgrounds, what makes this "Cinematic"? There are no transitions, no animations, and the UI is still static until the server pushes an update.

**Gaps:**
| Severity | Problem | Fix direction |
|---|---|---|
| Significant | Tooling Reality Gap | Rename `update_interface` to `update_status` or actually implement layout/component control. |
| Minor | Credibility of "Native" | Rebrand "Native Document Rendering" to "Real-time Document Previews" to manage expectations. |

## Persona 4 — The Grumpy Maintainer

You've built a "Server-Driven UI" that's going to be a nightmare to debug in 6 months.

- **Logic Duplication (The Transcript Trap)**: You have transcript rendering logic in `index.tsx` (lines 488-510) and `main_stage.html` (lines 310-330). If you want to change the "Gemini Architect" label, you have to do it in two places and two languages (TS and JS). 
- **Prop-Drilling via JSON**: Your `A2UI_STATE` (`main.py` lines 242-273) is a loose collection of objects. There's no TypeScript interface shared between the backend and frontend. If a developer renames `audioEnabled` to `isAudioOn` in `main.py`, the frontend breaks silently and just stops showing the controls.
- **Binary Fragility**: You're still calling `d2` and `rsvg-convert` via shell. If the Cloud Run environment changes or a package is updated, the whole "Architect" feature dies. You need a `/health` endpoint that actually verifies these binaries are functional.
- **State Inconsistency**: You have `ui_state` in `main.py` but the frontend also tracks `diagramMode`, `audioEnabled`, etc. If the WebSocket drops and reconnects, which state wins? You're setting yourself up for race conditions where the button says "ON" but the server thinks "OFF".

**Gaps:**
| Severity | Problem | Fix direction |
|---|---|---|
| Significant | State Split-Brain | Make the frontend purely reactive to the `A2UI_STATE` and remove redundant local state trackers. |
| Significant | Duplicate Transcript Logic | Centralize transcript formatting on the server and send the "ready-to-display" strings to both Side Panel and Stage. |
| Minor | Lack of Health Checks | Implement a startup verification for `d2` and `rsvg-convert`. |

## Panel Verdict

**Gaps by severity (cross-panel):**
| Severity | Gap | Persona(s) | Fix direction |
|---|---|---|---|
| **Critical** | XSS via `innerHTML` on Stage | Security | Use a safe rendering library (like `DOMPurify` on the client) or move to a non-HTML template system. |
| **Significant** | D2 Injection / LFR | Security | Implement strict sandboxing for the D2 binary. |
| **Significant** | Aspect Ratio Friction | UX | Adopt a responsive layout instead of fixed 16:9. |
| **Significant** | Transcript Overlap | UX | Prevent subtitles from blocking diagrams. |
| **Significant** | State Split-Brain | Maintainer | Unify state management; frontend should be a "dumb" renderer for `A2UI_STATE`. |
| **Significant** | Tooling Reality Gap | Credibility | Align tool descriptions with actual capabilities. |

**Exit criteria:**
- [ ] XSS risk on Stage eliminated (verified with payload test).
- [ ] D2 sandboxing or LFR protection implemented.
- [ ] Responsive layout on Stage (verified on mobile/narrow windows).
- [ ] Transcript/Diagram layout conflict resolved.
- [ ] A2UI is the "Single Source of Truth" for UI state.

**Recommended fix order:** [Critical XSS first, then D2 Security, then UX/Maintainability items]
